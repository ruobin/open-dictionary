# UI internationalization, theming & visual polish

This document covers three front-end systems added to the SPA:

1. **Internationalization (i18n)** — a four-language UI (English, Chinese,
   Japanese, Spanish) with a runtime language switcher.
2. **Theming** — a warm light theme, a dark theme, and a three-state toggle
   (light → dark → system).
3. **Visual polish** — a restrained refinement pass for an elegant, concise
   look across both themes.

These are client-only concerns; the Express API and the prerendered SEO pages
are unaffected (prerendered pages stay English-first for crawlers and hydrate
into the user's chosen language on load).

---

## 1. Internationalization

### Design

A deliberately lightweight, dependency-free i18n built on React context. There
is **no** `react-i18next` or similar runtime — the dictionaries are plain TS
objects, which keeps the bundle small and gives compile-time key checking.

### Files

- `src/i18n/translations.ts` — the four dictionaries (`en`, `zh`, `ja`, `es`),
  the `Locale` type, the `LOCALES` list, and native display names
  (`LOCALE_NAMES`). **English is the source of truth**: every other dictionary
  is typed `Record<TranslationKey, string>`, where `TranslationKey` is derived
  from `keyof typeof en`. This means a missing or typo'd key in any language is
  a **compile error**, not a silent runtime fallback.
- `src/i18n/I18nContext.tsx` — `I18nProvider` + `useI18n()` hook. Exposes
  `{ locale, setLocale, t }`.
- Wired into the tree in `src/main.tsx`, wrapping the whole app (outside
  `Auth0Provider`, since translations are needed even pre-login).

### The `t()` function

```ts
const { t, locale, setLocale } = useI18n()

t('nav.about')                              // "About" / "关于" / "概要" / "Acerca de"
t('word.notFoundTitle', { word: 'serendipidy' })  // → "We couldn't find "serendipidy""
```

- Keys are dot-namespaced by feature (`nav.*`, `auth.*`, `search.*`, `word.*`,
  `sidebar.*`, `history.*`, `about.*`, `report.*`, `moreExamples.*`, `home.*`,
  `theme.*`, `lang.*`, `common.*`).
- Interpolation uses `{placeholder}` tokens replaced from the `params` arg.
- Fallback order: current locale → English → the key itself.

### Locale selection

1. `localStorage['locale']` if present and valid.
2. Otherwise the browser's `navigator.language` prefix, if it's one we support.
3. Otherwise `en`.

On change, `<html lang>` is updated (for accessibility / search) and the choice
is persisted. The language switcher is a `<select>` in the header
(`LanguageSwitcher` in `src/components/Header.tsx`).

### Adding a new UI string

1. Add the key + English value to the `en` object in `translations.ts`.
2. `TranslationKey` auto-expands, so TypeScript now flags every other
   dictionary as incomplete — add the translated value to `zh`, `ja`, `es`.
3. Use `t('your.key')` (with `params` if interpolated) in the component.

### Adding a new language

1. Add the code to `Locale` and `LOCALES`, and the native name to
   `LOCALE_NAMES`.
2. Add a fully-populated dictionary (type it `Record<TranslationKey, string>`
   so the compiler enforces completeness) and register it in `dictionaries`.
3. Optionally extend `detectInitial()` if the browser prefix differs from the
   code.

### Scope notes

- **Dictionary entry content** (definitions, translations, examples) is
  generated by the LLM and returned by the API in the target language selected
  in the *search* controls — it is **not** part of UI i18n. The UI language
  switcher only affects chrome/labels, consistent with how most dictionaries
  work.
- The prerendered static pages (`scripts/prerender.ts`) are intentionally
  English-only: they exist for crawler SEO and no-JS clients, and hydrate into
  the user's chosen language once React mounts.

## 2. Theming

### Design

Two themes — a warm (yellow-ish) light theme and a dark theme — driven
entirely by CSS custom properties on `:root`. **No inline boot script** is used
(to respect the app's strict CSP: `script-src 'self'`, no inline scripts).

### How it stays FOUC-free

- `:root` carries the **light** defaults.
- `@media (prefers-color-scheme: dark)` applies the dark variables **unless**
  the user has explicitly chosen light (`:root:not([data-theme='light'])`).
- `:root[data-theme='dark']` forces dark.

So when the user hasn't chosen (the common case), the browser evaluates the
media query **before first paint** → no flash, and it tracks OS theme changes
live. An explicit choice writes `data-theme` and `localStorage['theme']`,
overriding the media query. (The only theoretical flash is if a user's saved
choice disagrees with their OS — negligible and resolved within the first
module tick.)

### Tokens

| Token         | Light (warm) | Dark       |
|---------------|--------------|------------|
| `--bg`        | `#fbf8f0`    | `#1e2432`  |
| `--bg-soft`   | `#f4ecdb`    | `#262c3b`  |
| `--ink`       | `#2a2620`    | `#ecebe7`  |
| `--ink-soft`  | `#5c5448`    | `#b8b5ad`  |
| `--muted`     | `#8a8170`    | `#8891a0`  |
| `--line`      | `#e6dcc6`    | `#343b4a`  |
| `--red`       | `#b81b21`    | `#e0625f` (brighter for contrast) |
| `--on-accent` | `#fbf8f0`    | `#1e2432`  |

`--on-accent` is the text color on red/ink accent surfaces (badges, primary
buttons) and flips with the theme for correct contrast.

All previously-hardcoded `#fff` / `white` values in `app.css` were replaced
with these tokens so every surface adapts.

### The toggle

`src/hooks/useTheme.ts` exposes a three-state choice
(`'light' | 'dark' | 'system'`). The header button (`ThemeToggle`) cycles
light → dark → system (GitHub-style) and shows a sun / moon / half-circle icon.
It listens to `prefers-color-scheme` so the resolved theme updates when the OS
changes while in `system` mode.

### Accessibility

`color-scheme: light` / `dark` is set on `:root`, so native form controls,
scrollbars, and the UA default background all match the active theme.

## 3. Visual polish

A restrained refinement pass (`src/styles/app.css`), not a redesign:

- **Typography**: subpixel antialiasing + `optimizeLegibility` text rendering;
  `text-wrap: balance` on display headings so headwords/titles break evenly.
- **Sticky header**: translucent (`color-mix` of `--bg` at 82%) with
  `backdrop-filter: blur(12px)` so content scrolls under a frosted bar.
- **Search field**: a soft resting shadow plus a `:focus-within` glow in the
  brand red (`color-mix` ring) — the primary entry point now feels responsive.
- **Word of the day**: promoted from a bare top-border to a soft rounded card
  so it reads as a distinct unit.
- **Chips**: a 1px hover lift (`translateY(-1px)`) and inverse fill for a
  tactile feel.
- **Selection & focus**: a branded `::selection` highlight and consistent
  `:focus-visible` rings (2px red) for keyboard users.
- **Scrollbars**: thin, themed, with rounded thumbs and a hover state.
- **Motion safety**: a `prefers-reduced-motion` block collapses transitions
  for users who request reduced motion.

All polish is expressed through the existing token system, so it inherits both
themes automatically.

## Deploy notes

These changes are **frontend-only** — no API, docker, or nginx changes are
needed. The build/deploy flow is unchanged:

```bash
npm run build                      # tsc --noEmit && vite build → dist/
npm run prerender                  # regenerate SEO pages into dist/ (needs Mongo)
# ship dist/ to the static root served by the host nginx
```

`color-mix()` and `backdrop-filter` are used for polish; both are widely
supported in current evergreen browsers. They degrade gracefully: a browser
that ignores `color-mix` falls back to the solid `--bg` declared immediately
before it on the header, and one that ignores `backdrop-filter` simply gets a
solid (still correct) header background.
